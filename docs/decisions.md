## 2026-11-09: Public defaults exempted in check:tracked

- Rule: `scripts/check-tracked-secrets.mjs` reads the tracked `supabase/functions/.env.example` and treats each non-empty `NAME=value` as a public default. That value is published in the tracked example file, so it is not a secret. Exact matching keeps every other `.my_env` value under check. `.my_env` and tracked files were not edited.

## 2026-11-10: Name rule helper in `src/domain/limits.ts` (task 4.1)

- design.md names the "name rules" in `limits.ts` but gives no helper signature. ## 2026-11-10: Bitmap codec in `src/domain/bitmap.ts` (task 4.3)

- `Result<T>` (`{ ok: true; value: T } | { ok: false; error: string }`, design: Domain components) is defined and exported in `bitmap.ts`, its first user. design.md names no file for it; later modules (`raster.ts`, `editor.ts`, `src/input/pointerMapper.ts`) import it from `bitmap.ts` unless a later task moves it.
- `decodeBitmap` checks, in order and before allocating output: `typeof text === "string"`, length exactly `LIMITS.bitmapBase64Chars` (6,828), `/^[A-Za-z0-9+/]{6827}=$/` (alphabet and single final `=`), alphabet index of character 6,826 with `index & 0b11 === 0`, decoded length 1,706 × 3 + 2 = 5,120. Any failure returns `{ ok: false, error }` and no bitmap.
- Encoder and decoder are table-driven (64-character alphabet string and a 128-entry `Int8Array` reverse table); no `atob`, `btoa`, `Buffer` or `TextEncoder`.
- `getPixel` and `setPixel` return an error for a non-integer or out-of-range coordinate, a value other than 0 or 1, or a bitmap that is not a 5,120-byte `Uint8Array`. `setPixel` writes to `b.slice()` and never modifies its input.
- `encodeBitmap(b): string` has no error channel in the design signature, so a bitmap that is not 5,120 bytes throws `RangeError`. This is the design's allowed programmer-error case: the `Bitmap` type promises 5,120 bytes. Callers pass only `createBitmap`, `setPixel` or `decodeBitmap` output.

## 2026-11-10: Property 8 generator (task 4.4)

- `tests/properties/raster.property.test.ts` drives Property 8 with 0–300 assignments. x is drawn from {0, 7, 8, 255} or 0–255, y from {0, 159} or 0–159, value from {0, 1}.
- fast-check's default `size` keeps generated arrays short (about 10 elements), so the sequence arbitrary is `fc.oneof` of the default-size array and an array with `size: "max"`. Coverage measured on seed 20261108, 500 runs: lengths 0–298, 34 empty runs, 155 runs longer than 100, 245 runs that write one pixel more than once, all of x ∈ {0, 7, 8, 255} and y ∈ {0, 159} generated.
- The oracle is a `Uint8Array(40960)` with one entry per pixel, packed MSB-first in the test and compared with `Buffer.from(bytes).toString("base64")`. Its constants (256, 160, 5,120, 6,828) are written in the test, not read from `LIMITS`.
- Req 8.2 "identical text for equal pixels" is checked by rebuilding the same pixel array from only its ink pixels in index order and comparing the encoded text.
- The all-black bitmap is not generated: Property 8 starts from blank with at most 300 writes. The all-white (blank) bitmap is the empty sequence.

## 2026-11-10: Dither_Fill region and pattern (task 6.3)

- `fillRegion(b, seed): Uint32Array` in `src/domain/raster.ts` follows the design signature and returns region indices `y·256 + x` only; it never writes to `b`. Applying `ditherPattern` and the noop rule stay in `fill/apply` (task 7.6).
- Gap: design.md does not say what `fillRegion` does with a seed outside 0–255 × 0–159. Chosen: an integer seed outside the card returns an empty `Uint32Array`, which `fill/apply` treats as "no pixel would change" (Req 10.7). A non-integer seed or a bitmap that is not 5,120 bytes throws `RangeError`, as `linePixels` and `encodeBitmap` do for programmer errors.
- Region order is ascending index (row-major): after the stack drains, one scan of `visited` collects the region, so the output does not depend on traversal order. design.md's pseudocode adds pixels at pop time; the set of pixels is the same.
- Fill buffers per call: `visited` `Uint8Array(40960)` and stack `Int32Array(40960)`, marked at push time so the stack cannot exceed 40,960; no recursion and no per-pixel objects.
- `src/domain/dither.ts`: `BAYER4` and its rows are `Object.freeze`d; `DITHER_LEVEL = 6`; `ditherPattern(x, y) = BAYER4[y & 3][x & 3] < 6 ? 1 : 0`. `& 3` equals mod 4 for negative integers too. A non-integer coordinate throws `RangeError`; design.md gives no error channel for it.

## 2026-11-10: Pointer mapping in `src/input/pointerMapper.ts` (task 10.1)

- `logicalPoint(clientX, clientY, rect, width = 256, height = 160): Result<Point>` as in design.md. Defaults come from `LIMITS.cardWidth` and `LIMITS.cardHeight`; `Result` is imported from `src/domain/bitmap.ts` and `Point` from `src/domain/raster.ts` (type-only). The rect type is exported as `PointerRect`, structurally the same as the design's inline type.
- Formula and operation order are blueprint §2.7 exactly: `clamp(floor(((clientX − left) × width) / rect.width), 0, width − 1)`, same for y. The function is pure and reads no DOM; the CanvasView adapter (task 13.2) passes the rectangle it re-read for each sample.
- Error shape: design.md gives no error text, and `Result` carries a string. Every error starts with the exported constant `INVALID_GEOMETRY` (`"invalid-geometry"`), then `: <detail>`. Callers and the Property 16 test (task 10.2) should match the prefix, not the detail.
- Checks run in this order: clientX/clientY finite; left/top finite; rect width/height finite; rect width/height > 0. Addition beyond Req 14.2: the logical `width`/`height` parameters must be positive safe integers, otherwise the same error. With the defaults this never fires; it keeps the 0…width − 1 output range true for any caller.
- Finite inputs whose difference overflows (for example 1.7e308 − (−1.7e308)) give ±Infinity, which the clamp maps to the edge pixel. NaN cannot arise from finite inputs with a positive finite rect size; a NaN guard after the clamp returns the error anyway, so the function never returns NaN. `-0` cannot be returned: `Math.max(0, -0)` is `+0`.
- `src/input/` is compiled by `tsconfig.app.json` only (design: Architecture). `check-domain-imports` scans `src/domain/` only, so it does not cover `src/input/`; importing from `../domain/` is allowed there.

## 2026-11-10: `validateStack` in `src/domain/schema.ts` (task 5.3)

- `Diagnostic.references` (D-C) added in task 5.3. `validateStack` never sets it.
- Passes are short-circuited: zod runs only when the structural pre-pass found nothing, and the semantic checks run only on a zod-parsed document. On success `value` is zod's output, a fresh copy that never aliases the candidate.
- Nesting depth: the root container is level 1. A container whose path has 8 or more segments (level 9) gets `too-deep` at its path and is not entered. Valid documents reach level 5. The depth cut also ends any reference cycle in an in-memory candidate. An object shared at several places is walked once per place (no visited set); JSON input cannot share objects.
- Pre-pass order is pre-order with `Object.keys` order and array index order. The value under a forbidden key is never read.
- zod mapping: `unrecognized_keys` → one `unknown-property` per key with the key appended to the path. `invalid_type` → `missing-property` when the parent has no own property for the last path key, else `wrong-type`. `invalid_union` (discriminator; zod puts `kind` in the path) → `missing-property` if `kind` is absent, else `invalid-value`. `invalid_value` → `invalid-value`. `invalid_format` and `invalid_key` → `invalid-id`. `too_big`/`too_small` (unsafe integers from `z.number().int()`) → `invalid-value`. Diagnostics keep zod's issue order: schema key order per object, with unknown keys after the known ones.
- Semantic order (documented at `semanticPass`): title; `cardOrder` entries, then unlisted card keys; card count; each card in `cards` key order (id = key, id unique, name, name unique, bitmap, widget count, then each widget: id unique, name, name unique, x, y, width, x + width, height, y + height, Button source); Canonical_Form size last, at the root path `[]`. design.md says "pass order, then document order"; the size check sits last because it measures the whole document.
- Duplicates are reported at the later occurrence, with `otherPath` set to the first one. `cardOrder` duplicates use `card-order` with `otherPath`.
- Gap, chosen: names are checked for uniqueness only when they pass the name rule. An empty or over-long name is already reported, and this keeps the quoted value in the message to at most 64 code points.
- Gap, chosen: ID uniqueness covers Card and Widget IDs (Req 6.6), lowercased. The stack `id` is not compared with them. design.md's "no ID shared by two objects" could be read to include the stack; Req 6.6 names only Cards and Widgets.
- `measured`/`max` are set on `card-limit`, `widget-limit`, `source-too-large` and `document-too-large`. `cards-empty` carries `measured: 0` and no `max`, since 1 is a minimum. Geometry diagnostics carry neither; their message states the sum.
- No diagnostic cap. A JSON file can yield one diagnostic per offending key; the Importer's 1 MiB byte limit bounds the count.

## 2026-11-10: Shared test generators in `tests/properties/arbitraries.ts` (task 5.4)

- `stackDocumentArb` builds valid documents without `fc.pre` or whole-document filtering. Card names and Widget names per Card are unique through `fc.uniqueArray` (selector `name`). Stable_IDs are unique when lowercased through a repair pass that replaces a repeated generated ID with an ID from `counterIdSource({ namespace: 0x9e9e0000 })`. `cardOrder` is the generation order; `cards` keys are inserted in a different, generated order. The stack `id` is not made unique against Card or Widget IDs, matching the task 5.3 choice.
- Bias and boundaries: card counts come from `fc.oneof` of a default-size array (weight 6), exactly 1, exactly 20 and a `size: "max"` array; widget arrays likewise (default size, `[]`, exactly 40, `size: "max"`). Names: mostly 1–12 code points, with branches for exactly 1 and exactly 64 code points, a `size: "max"` branch and curated astral and combining names. Geometry: x from {0, 255} or 0–255, y from {0, 159} or 0–159, width and height "min" (1), "max" (touches the right or bottom edge) or random. Bitmaps: all paper, all ink (every byte 0xFF), 32-bit-seeded xorshift random bytes, or 1–16 ink pixels at boundary coordinates. Button sources: short text, or one of five fixed strings of exactly 8,192 UTF-8 bytes (1-, 2-, 3- and 4-byte code points). This closes the all-ink gap of the task 4.4 entry.
- Strings contain whole code points only, never a lone surrogate, so documents survive a UTF-8 export and import (Property 6). Short text includes JSON escapes (`"`, `\`, U+0000, U+001F, CR, LF, U+007F).
- Size budget: at most 400 Widgets per document (later Cards are trimmed) and at most 8 Button sources over 1,024 bytes (further ones become ""). The worst-case escaped estimate is about 551,000 bytes, below 1,048,576 with room for the largest injected fault. Documents with 20 Cards × 40 Widgets and the exact 1,048,576-byte document stay in unit test 5.8.
- `counterIdSource({ namespace, start })` yields `NNNNNNNN-0000-4000-8000-CCCCCCCCCCCC` (namespace in 8 hex digits, counter in 12). Each call starts a fresh sequence, so the same options give the same IDs.
- `faultArb(doc, kinds?)` and `documentWithFaultArb` inject one fault into a `structuredClone` of the document and record `{ kind, candidate, path, expectedCode, otherPath?, measured?, max? }`. Fault kinds and the codes `validateStack` emits: card-limit (21–25 Cards, `card-limit` at `cards`), widget-limit (41–44, `widget-limit` at the Card's `widgets`), source-too-large (8,193, 8,194, 8,195 or 10,000 bytes, `source-too-large`), non-finite-number (NaN, ±Infinity in any number), forbidden-key (own `__proto__`, `constructor` or `prototype` on the root, `cards`, a Card or a Widget), unknown-property (`theme`, `zoom`, `selection`, `history`, `playState`, `cursor` or a random key), missing-property, wrong-type (another JSON type for a string, integer, array or object property), schema-version (0, 2, −1, 1.5, 2026 or "1", `invalid-value`), duplicate-name (`name-duplicate`, later path plus `otherPath`), duplicate-id (a Widget ID set to an earlier ID in the same, upper or lower case, `id-duplicate` plus `otherPath`), name-rule (`name-empty`, `name-too-long` with 65–80 code points, `name-whitespace-only`). ## 2026-11-11: Editor core and card actions in `src/domain/editor.ts` (task 7.1)

- Types as in design.md: `EditAction` (full union), `EditorContext { newId, references }`, `ReferenceIndex` (defined in `editor.ts`, where the design puts it), `EditResult`. `applyAction` follows the four-step contract: build the candidate, `noop` if structurally equal to the input, `rejected` with the `validateStack` diagnostics, else `applied` with the candidate. The candidate, not zod's parsed copy, is returned so unchanged Cards stay shared with the input (design: Edit history memory note). `noop` carries no document (design `EditResult`); the caller keeps its reference.
- Editor rules are checked before a candidate is built, so a rejected action never calls `ctx.newId`: unknown ID, then `card-limit` (add), name rule then `name-duplicate` (rename), `last-card` then `referenced` (delete). When both `last-card` and `referenced` apply, `last-card` is reported (design.md gives no order; it needs no port call).
- New `DiagnosticCode`s (design.md has none for these): `card-not-found` (an action names a Card that is not both a `cards` key and in `cardOrder`; path `["cards", <id>]`), and `action-unsupported`, temporary, returned for `widget/*`, `stroke/commit` and `fill/apply` until tasks 7.3 and 7.6 implement them; those tasks remove the code and its cases. The `default` branch of the action switch is a `never` check, so a new union member without a case fails typecheck.
- `card/add`: `card-limit` at `["cards"]` with `measured` = count + 1 (the count the add would produce, as `validateStack` would report for the candidate) and `max` 20. Name "Card N" with the smallest positive N no Card has (exact, case-sensitive). Inserted after `afterCardId`; the new Card's ID is `cardOrder[indexOf(afterCardId) + 1]` of the result. One `ctx.newId()` call. Label "Add card".
- `card/rename`: the name is stored exactly as given (no trimming). Name-rule and duplicate diagnostics are produced by the editor at `["cards", <renamed id>, "name"]`, with `otherPath` on the other Card for `name-duplicate`, because `validateStack` reports a duplicate at the later Card in key order, which may be the other Card. Codes and message tails are the same as `validateStack` (`NAME_RULE_CODE`, `NAME_RULE_MESSAGE`, now exported from `schema.ts`). Renaming to the current name is a `noop`. Label "Rename card".
- `card/move`: swap with the neighbour; first Card earlier or last Card later is a `noop` with no candidate. Labels "Move card earlier" / "Move card later".
- `card/delete` and the Reference_Index: the glossary defines the index per target (a Card, or a Widget). The editor queries the Card first, then each Widget on it in array order, and lists each `{cardId, widgetId}` once at its first position, so the order is the index's order (D-C). One `referenced` diagnostic at `["cards", <id>]` with fresh `references` objects. References from Buttons on the Card being deleted are not excluded; design.md does not say to, and the real index arrives in spec 02. Label "Delete card".
- `currentCardAfterDelete(cardOrderBefore, deletedId, currentId)`: unchanged if another Card was current; else the follower, else the predecessor (Req 7.12).
- `createBlankStack`: draws the stack ID, then the Card ID; title "Untitled stack", one blank "Card 1". `forkStack`: fresh stack ID, every object and array copied (strings shared), Card and Widget IDs kept. Neither validates its output; with a valid `IdSource` both pass `validateStack` (checked below).
- Noop check: `documentsEqual` is a structural JSON equality with reference fast paths; object key order is ignored (the `cards` key order is not part of Canonical_Form), array order is not.

## 2026-11-12: Stroke and fill actions in `src/domain/editor.ts` (task 7.6)

- `stroke/commit`: unknown Card first (`card-not-found`), then the samples, then `decodeBitmap` of the Card's bitmap; `applyPolyline` writes 1 (Pencil) or 0 (Eraser) into that fresh decoded array only (D-A); the result is encoded once. Copy-on-write along `cards → card`; other Cards and the Card's `widgets` array are shared by reference.

A non-object sample gives `invalid-value` at `["samples", k]`.
- Empty samples: design.md defines a Stroke as having a first sample (Req 9.8, Property 10 "non-empty sample list") and does not define the empty case. Chosen: rejected as `invalid-value` at `["samples"]`, not `noop`.

No `setPixel` and no per-pixel objects. No pixel changed means `noop` (Req 10.7).
